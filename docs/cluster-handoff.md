# Cluster prototype integration handoff

Integrate this prototype into the existing cluster for an instructor-controlled
pilot. The user now wants the whole platform in the cluster, rather than local
preview or local development. Preserve Autolab/Tango and existing databases.
Do not enroll real students or create their repositories as part of setup.

Source: `git@github.com:martin-fink/srg-grading.git`.
Application revision inspected: `3cc952dfd0078408e260eb3a3da9148bb278b9e2`.
This handoff is a subsequent documentation addition; obtain it alongside that
revision or use a later reviewed commit containing it. Do not assume local changes

## What exists, and what you must implement

Read `README.md`, `docs/operations.md`, `docs/grading.md`, and
`docs/acceptance.md`. Application source, migrations, Nix packages and container
images exist. `nix/compose.yaml` describes VM-side services and their exact commands,
mounts, credentials, and limits. Translate those into the cluster's existing
deployment/GitOps conventions. It is not a Kubernetes manifest.

`nix/kubernetes.yaml` provides only sandbox namespace policy, quotas, and executor
RBAC. It does not install gVisor, a PVC, an executor, the web service, or PostgreSQL.
`nix/executor.toml.example` is a configuration example with placeholder image values.
The live GitHub App flow and actual gVisor grading still require pilot validation.

Discover existing ingress/TLS, secret management, registry, node architectures,
storage classes/access modes, CNI policy enforcement, backup destination, and
gVisor support before choosing concrete resources. Use established infrastructure
mechanisms rather than introducing a second provisioning system.

## Build and distribution

GitHub CI is not required. Build on a trusted Nix machine or matching remote builder:

```sh
nix develop -c just check
nix develop -c just test
nix build .#web-image -o result-web
nix build .#cli-image -o result-cli
nix build .#postgres-image -o result-postgres
nix build .#executor-image -o result-executor
```

These outputs are Docker-loadable image archives, named `grading-web:prototype`,
`grading-cli:prototype`, `grading-postgres:prototype`, and
`grading-executor:prototype`. For example, on a builder with Docker:

```sh
docker load < result-web
docker tag grading-web:prototype REGISTRY/PROJECT/grading-web:SOURCE_REVISION
docker push REGISTRY/PROJECT/grading-web:SOURCE_REVISION
```

Repeat for the other images, capture registry digests, and deploy digest references.
Use the existing registry import mechanism if Docker is unavailable. Build for
the actual Linux node architecture; an ARM archive is not an x86 image. Nix does
not automatically make these multi-architecture images. Course grading images
are additional, independently approved images; these four do not include them.

CI can later run the same checks/builds and publish images. It needs no runtime
App key, DB passwords, worker tokens, or student records. New files must be tracked
before Git-flake builds will include them.

## Workloads and identities

Start with one web replica, one task processor, one executor and one dedicated
PostgreSQL instance. Do not use Astrid's shared PostgreSQL.

| Workload | Image / command | Credentials and storage |
| --- | --- | --- |
| PostgreSQL StatefulSet | postgres image entrypoint | UID 10002; DB PVC; bootstrap password files; writable `/run/postgresql` and `/tmp` |
| Migration Job | CLI image, `--database-url-file … migrate` | UID 10001; owner DB URL only |
| Web Deployment | web image; arguments from Compose | UID 10001; web DB URL, App config/key, webhook secret; artifacts volume |
| Task Deployment | CLI image, `… work` | UID 10001; web DB URL, App config/key; same artifacts volume |
| Operator Jobs | CLI image, imports/sync/worker registration | operator DB URL; App config/key when needed; artifacts and private course checkout as needed |
| Admin Jobs | CLI image, `admin grant/revoke/list` | admin DB URL only; outbound GitHub lookup; audited operator identity |
| Executor | executor image, `--config /run/secrets/executor.toml` | UID 10004; worker token, TLS client identity/CA, restricted Kubernetes identity, source staging volume |
| Student Jobs | approved course image, generated by executor | UID 10003; no credentials; read-only source subpaths and bounded ephemeral workspace |

Use separate namespaces for trusted application services and untrusted jobs. An
executor Pod needs the same PVC namespace as its generated jobs unless the storage
design explicitly exposes the same dedicated backing storage across namespaces.
One workable layout places the trusted executor in the sandbox namespace with a
dedicated ServiceAccount and narrowly selected egress policies; student Pods retain
default-deny networking. Never put executor credentials on the staging PVC.

The sample RoleBinding targets a Kubernetes User named `grading-executor`.
For an in-cluster executor, adapt it to the actual dedicated ServiceAccount. Only
the executor gets its token. Web, tasks and student Pods must not receive Kubernetes
credentials. Keep RBAC limited to the sample namespaced Jobs/Pods/log operations.

All workloads: non-root, no privilege escalation, dropped capabilities, bounded
resources/logs, read-only root filesystem and explicit writable mounts. Preserve
the separate DB roles and credentials; runtime roles must not grant administrators
or assume owner/admin roles. Mount secrets as files using the existing secret
management mechanism. No secrets in Git, Nix store, images or command-line values.

## Storage and networking

- Web and tasks must see identical artifact files. Choose supported shared storage
  or enforce compatible co-location; two independent PVCs are not equivalent.
- Executor staging and sandbox source mounts must see identical paths. Generated
  Jobs reference `source_pvc` and per-lease subpaths relative to `staging_root`.
  Plan access mode and scheduling for executor plus grading Pods, not just one Pod.
  Check UID 10004 writes and UID 10003 read/traverse access on actual storage.
- DB data is mounted only by PostgreSQL. Use private ClusterIP access with SCRAM,
  no public ingress/NodePort/LoadBalancer for PostgreSQL, and restrictive policies.
- Web listens on `0.0.0.0:8080` for browser/webhook traffic and `0.0.0.0:8081` for
  the worker API. Set both flags explicitly; defaults bind only to loopback.
- Public HTTPS ingress goes only to 8080. `/healthz` is liveness; `/readyz` checks DB
  readiness. Do not expose the worker port through the public ingress.
- Executor API uses a separate HTTPS endpoint to 8081, restricted to the executor,
  with client-certificate validation at the proxy. The application itself serves
  HTTP on these listeners; bearer tokens alone do not implement mTLS termination.
- Allow trusted services the necessary DNS, DB, GitHub and worker API access.
  Only executor can reach Kubernetes API. Student Pods have no network access.
  Verify enforcement rather than merely creating NetworkPolicy objects.

Adapt the sample quota and Pod Security version to the real cluster and approved
budget. Ensure gVisor RuntimeClass exists on the selected nodes, node PID limits
and log rotation are enforced, and scheduling actually uses those nodes. If these
are unavailable, stop before executing student code; do not fall back to privileged
containers or the general-purpose Actions runner pool.

## Secrets and GitHub setup

Use the file formats and PostgreSQL bootstrap file names in `docs/operations.md`
and `nix/compose.yaml`. URL passwords must match their role's bootstrap passwords.
The PostgreSQL entrypoint creates roles; the migration Job creates schema/grants.

Configure one organization-installed GitHub App for this deployment. Supply real
App ID, installation ID, client ID/secret and PEM key in runtime files. Set:

- Public origin: `https://CHOSEN_PUBLIC_HOST`.
- App callback: `https://CHOSEN_PUBLIC_HOST/auth/callback`.
- Push webhook: `https://CHOSEN_PUBLIC_HOST/webhooks/github`.
- Webhook secret: the exact bytes in the web secret file, at least 32 bytes.

Validate the App permissions listed in operations.md in the test organization,
including coverage of newly created repositories. Base access must be none;
general-purpose self-hosted runner groups must be inaccessible to student repos.

## Bring-up order

1. Obtain source, run checks, build/publish images and record digests.
2. Provision namespace isolation, secrets, storage, dedicated DB, TLS and policies.
3. Wait for PostgreSQL, then run the owner-credential migration Job successfully.
   Never give the web container migration credentials.
4. Start web and `gradingctl work`; verify readiness and real GitHub login.
5. Through the dedicated admin Job, run:
   `gradingctl --database-url-file /run/secrets/database-url admin grant --github-username martin-fink --reason "Cluster pilot administrator"`.
   Supply the actual host/operator identity through the existing trusted Job launch
   mechanism. All human GitHub identity inputs use handles; the CLI resolves IDs.
6. Configure independent executor profile allowlists, image digests, commands and
   resource caps. Generate a worker token, register it with the operator credential
   using `gradingctl worker register --id astrid-1 --token-file … --profile functional-v1 --cpu … --memory-gib … --storage-gib …`,
   then start the executor with matching configuration. It gets no DB/App secrets.
7. Create a small instructor-owned functional stdin/stdout exercise, public tests,
   pinned template/image, and generated private manifest. Commit private course
   configuration and manifest to its own repository. Import course and roster with
   dry runs first; use only instructor-controlled student accounts. Fixtures contain
   placeholders and must not be deployed as real configurations.
8. Test Create repository, invitation, push receipt, immutable snapshot, integrity
   check, real sandbox grading, points and exact-SHA GitHub Check end to end.
9. Schedule daily `gradingctl sync` with operator credentials, shared artifacts
   and App config. It uses a DB advisory lock. If using a CronJob, deliberately set
   and test missed-run catch-up semantics; the existing systemd timer is not a
   Kubernetes resource. Keep continuous tasks running independently.
10. Adapt backup/restore and monitoring to this deployment. `nix/backup.sh` currently
    assumes Docker Compose; port its dedicated DB dump + artifact capture to the
    established encrypted Borg destination. Do an isolated restore before pilot use.

## Acceptance and reporting

Run the external cases in `docs/acceptance.md`. Especially verify secret/network
isolation from a real sandbox, source PVC visibility, App provisioning permissions,
integrity rejection, resource limits, worker restart/lease recovery, deadline/lock
behavior, and DB plus artifact restoration. The current harness is functional
stdin/stdout comparison; LLVM/FPGA/SimBricks compatibility is not established.

Return the infrastructure changes, source/image digests, endpoint URLs, namespace
and storage choices, exact operator commands, validation evidence, remaining gaps,
and rollback steps. Never print secret contents. Do not declare deployment complete
merely because the web page loads. Leave Autolab/Tango and its backups untouched.
